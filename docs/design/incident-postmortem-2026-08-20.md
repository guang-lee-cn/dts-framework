**摘要（三行）**：

1. 自研桶传输的接收线程按调用方传入的 `max_msg_size = UINT32_MAX` 预分配接收缓冲——`vector(4GB)` × 3 通道 × 2 进程，吃满 21.5GB WSL，OOM 连杀、虚拟机崩溃，共 4 次（08-17 ×2，08-20 ×2）。

3. 修复一行钳制（commit `6ef520e`）；复盘转化出工具护栏 / SOP / 契约三类资产（§5），全部落地。

## 2. 根因链

```
FastDDS 非 secure 模式：参与者侧 max_receiver_buffer_size = UINT32_MAX（写死）
  ↓ NetworkFactory: min(transport值, 参与者值) —— 两端皆上限值，min() 形同虚设
  ↓ OpenInputChannel(locator, receiver, max_msg_size = 4294967295) 原样下发
  ↓ 桶收线程 std::vector<uint8_t> buf(max_msg_size_) → vector(4GB) 且置零摸满
  ↓ 每进程 3 输入通道（元组播/元单播/用户单播）= 12GB × pub/sub 两进程
  ↓ WSL 21.5GB 吃满，swap=0（配了 8GB 未生效）无缓冲
  ↓ OOM 连杀 → VM 崩溃 → 会话断连 ×4
```

### 2.1 为什么内置 SHM 返回同值却不炸（本案核心机理）

关键差异在一件事情上：**收到的消息字节放在哪里**。

**内置 SHM 的收线程**（`SharedMemChannelResource.hpp:124`）：

```cpp
std::shared_ptr<SharedMemManager::Buffer> message;
message = Receive(remote_locator);            // 从共享内存段的环里取"槽位句柄"
message_receiver()->OnDataReceived(
    static_cast<octet*>(message->data()),     // ← 指针直接指向段内，原地解析
    message->size(), ...);
```

发送方把载荷 memcpy 进共享内存段后，字节**不再挪窝**；接收线程拿段内指针交给协议栈原地解析。在它那里"接收缓冲区"这个概念**根本不存在**——段本身就是缓冲区，而段的大小是**创建时**由配置定死的，与 FastDDS 后续传入的 `max_msg_size` 无关。

**桶传输 v1 的收线程**（修复前）：

```cpp
std::vector<uint8_t> buf(max_msg_size_);      // ← 私有堆预分配，按调用方的值开 4GB
segment_->Read(buf.data(), max_msg_size_, len, ...);   // 每条消息从段里拷出来
```

三种传输对照——同一个 `max_recv_buffer_size()` 返回值，三种命运：

| | 返回值 | 消费方式 | 接收缓冲 | 后果 |
|---|---|---|---|---|
| 内置 UDP | 有界（maxMessageSize） | 按值分配 | 私有，= 返回值 | 有界，安全 |
| 内置 SHM | UINT32_MAX | **不分配**（段内原地读） | 不存在（段即缓冲） | 安全 |
| 桶 v1（修复前） | UINT32_MAX（抄 SHM） | 按值分配（UDP 式） | 私有，= 返回值 | **4GB × 3 通道** |

一句话：**SHM 返回 UINT32_MAX 是"能力声明"（别拿报文尺寸约束我，反正我不按它分配）；桶 v1 把它当成了"分配尺寸"。抄了 SHM 的返回值，实现了 UDP 的消费方式——抄了一半。**

v1 选"take 拷贝形态"（2 拷贝版先行、免 loan 归还负担）本身是合理的设计决策，修复后亦保持（实测 200×32K 零丢、~325MB/s）；错的不是要拷贝，而是拷贝目的地的大小用了别人的上限声明，而不是自己配置的 `maxMessageSize`（8MB）。

## 3. 为什么没拦住（三道防线逐条检视）

| 防线 | 缺位 |
|---|---|
| **测试** | bucket 测试设计了"无 /dev/shm 自动 Skipped"，此前所有验证都走了跳过分支；开发机 /dev/shm 一直可用，08-17 16:23 是该路径**首次真跑**——"沙箱验证通过"给从未执行的代码发了通行证 |
| **护栏** | 新路径首跑无任何资源上限（无 ulimit、无内存监控），失控直接打穿到虚拟机层 |
| **证据保全** | VM 崩溃带走页缓存中未落盘的 ctest 日志，"测试到底跑没跑"长期成谜，拉长排查 |

## 4. 为什么走了弯路（前提陷阱命中 4/5）

| 陷阱 | 本案命中方式 |
|---|---|
| ① 验证过 = 没问题 | "沙箱 Skipped 验证过机制正确" ≠ 真跑过；环境分叉未识别 |
| ② 文档记录 = 事实 | worklog 记了"Skipped（shm 不可用）"，排查时以此排除了 bucket 嫌疑——文档只记录了它看到的分支 |
| ③ 时间相关 = 因果 | 断连时刻恰能对上全天候网络噪声（CheckConnection 本 boot 283 次），真病掩护了死因 |
| ⑤ 没跑起来 = 没执行 | tee 日志缺失被误读为"命令从未执行"；实际已执行，结果随崩溃丢失 |

**方法层遗漏**：首轮排查只查当前 boot 的 dmesg，未跨 boot 搜 OOM 历史——
`journalctl -k --since 2026-08-17 | grep 'Out of memory'` 一条命令 5 秒可锁定凶手。

**转折点**：带护栏的受控复现（`ulimit -v 3GB`，保证杀不死机器）+ strace 抓分配形态（4GB mmap 一眼定罪）。"一跑就崩机"类 bug 的标准姿势：**先上枷锁再复现，用分配轨迹代替猜测**。

## 5. 改进措施（双环 + 资产载体）

**双环学习**：

- **第一环（修行为）**：`OpenInputChannel` 钳制收缓冲尺寸
- **第二环（修心智）**："验证过"降级——验证过的永远只是"某环境 × 某路径"的组合，任一变化即失效；复用参考实现的接口值，必须先核对其**消费方式**

| 措施 | 载体 | 状态 |
|---|---|---|
| 测试脚本 `ulimit -v 3GB` 内存护栏 | 工具 | ✅ ctest 带帽全过 |
| 崩溃/断连排查第一动作 = 跨 boot 搜 OOM/panic 史 | SOP（incident-review §2） | ✅ |
| `max_recv_buffer_size` 返回值 = 真实可分配上限 | 契约（代码注释 + 本文 §2.1） | ✅ |
| Windows 侧确认 swap=8GB 为何未生效（本次放大器） | 环境配置 | 用户侧 |

**护栏边界（明确不遮羞也不越权）**：

| 故障类型 | 护栏行为 | 说明 |
|---|---|---|
| 失控型（分配直到吃满，本案） | `bad_alloc` → abort → 测试红 | **不掩盖，反而显性化**：把"崩宿主机/丢证据/数小时"降级为"一条红测试/分钟级" |
| 慢性小泄漏（始终在帽下） | 不拦 | 加帽前后测试同为绿，非"掩盖"而是本就无检测手段——归 **LSan / 内存基线断言** 管（护栏防事故突变量，基线断言防劣化缓变量，互补不互代） |
| 误杀（合法大内存需求撞帽） | 显性失败 | 日志直指 bad_alloc；处置原则见脚本注释：先查泄漏，不是调大帽子 |
