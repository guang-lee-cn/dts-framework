# 2026-08-17：确定性预算基石（节拍准点 + 帧耗时打点 + 丢弃计数）+ 容量核算

> 背景：5G 基站数据采集中间件落地评估。需求口径（用户确认）：
>   · 事件驱动：周期 tick 由外部 pub 端控制，本线程体现周期处理（不需要中间件自持上报节拍）
>   · 确定性预算：data 线程内单消息处理（出 mailbox → 处理完成含业务代码）≤ 5ms，预留处理上限
>   · 上报粒度：每帧到即上报（直通模式保持）
>   · 负载：100 帧 32K / 100ms（≈1000 帧/s，32MB/s）

## A. 容量核算（确认负载代入）

| 项 | 值 |
|---|---|
| 到达速率 | 1000 帧/s ≈ 32MB/s |
| 接收上限（bench 实测） | 950 帧/s ≈ 30MB/s（FastDDS BytesType::deserialize 瓶颈） |
| 结论 | **持续负载超上限 ~5%，零余量** → 100ms 周期稳态必然积压/丢帧 |
| 突破路径 | raw 固定大小 plain 类型 + DataSharing loan 零拷贝（文档既定方向，P0） |
| 线程内单帧预算 | 1KB 帧实测 max 1.5ms（含首帧预热）/ 稳态 ~0.4ms → 5ms 预算名义余量充足（32K 帧需真实硬件实测） |

## B. 落地：确定性预算基石

1. **ThreadRun 节拍改绝对期限**（P0-A，修真 bug）：
   - 旧：相对期限 wait_until(now+100ms) —— 持续负载（mailbox 恒非空）下永不超时，
     TIMER 永不投递 → TTL 回收停摆 → 池满静默丢帧（100ms 周期多帧负载必现）
   - 新：nextDeadline 绝对期限，到点强制投 TIMER（优先于消息）；追赶跳过不连投；
     jitter ≤ 单条消息处理时间（预算兜底）
   - 回归测试 unit_thread_tick：持续 5ms 间隔消息 1.5s，断言 TIMER ≥10 次（旧实现=0）

2. **data 单帧处理耗时打点**（P0-B）：
   - DataFactory::Process 内测量（口径：线程内处理含业务代码）
   - 阈值 data_config.h：kFrameBudgetWarnUs=3ms 预警 / kFrameBudgetAlarmUs=5ms 告警
   - 统计：frames / frameMaxUs / warn / alarm 计数（原子，DataStats）

3. **静默丢弃计数**（P0-C）：池满（AcquireBlock 失败）整帧丢、上报帧超容丢切片
   （ReportAggregator::Drops）、帧头解析失败（keyFail）——全部计数不静默

4. **console get_data_stats**：帧耗时预算 + 丢弃计数查询（实测输出见下）

5. **帧头解析对齐修复**（前置真 bug）：ExtractKey 曾用 uint32_t* 错位读取 raw 帧头
   （布局 [u16 dataType][u32 cellId][u32 cpId]），导致所有小区 hash 键错乱、共享同一
   cache block；改按字节偏移 memcpy 解析，暴露 ExtractRawKey + 单测回归；
   OnAgentData 的 dataType 读取同步改 memcpy（可非对齐）

## C. 实测（沙箱 1KB 帧链路）

```
frames=30 max_us=1501 warn3ms=0 alarm5ms=0 ticks=118
drop_pool_full=0 drop_slice_overcap=0 key_fail=0
```
- ticks=118（~10/s）：**持续负载下节拍准点**（饿死 bug 修复的活证据）
- max_us=1501 含首帧预热（registry 诊断/分配器/DDS 首写）；稳态 ~0.4ms
- key_fail=0（对齐修复后）；修复前错位读导致键错乱（影响多小区缓存语义）

## 追加：P0-2 RT 严格模式 + P1-1 预算阈值可配置

**P0-2（DTS_STRICT_SCHED=1）**：detsched RT 创建失败时——默认降级 SCHED_OTHER（dev 兼容）；
严格模式 = 拒绝启动（fail-fast，无确定性保证不许静默运行）。实测：沙箱无 RT 权限 +
DTS_STRICT_SCHED=1 → exit=1 + Error（"refusing to run without real-time scheduling"）。

**P1-1（预算阈值可配置）**：data 帧耗时预算阈值从编译期常量改为——
- 环境变量 DTS_DATA_BUDGET_WARN_US / DTS_DATA_BUDGET_ALARM_US（构造时读取，部署按硬件档位定）
- console `set_data_budget <warn_us> <alarm_us>`（运行时调整，warn≤alarm 校验）
- `get_data_stats` 输出当前阈值（budget_warn_us/budget_alarm_us）
实测：env 覆盖生效（800/1200）、运行时调整生效（1000/4000）、非法值拒绝。

## 追加：P1-2 指标出口（OAM 业务组）+ 沙箱跨进程环境限制定界

**实现**：
- dts_def.h：MSG_ID_OAM_STATS_REQ/RESP + SESSION_INST_OAM
- data 线程新增**运维业务组**（sessionInst="oam"，挂在 data 线程，组间 msgId 独立
  编号）——完整演示"同线程挂新业务组"配方（config 端点 + 组数组加项 + 组内消息表）
- OnOamStatsReq：DataStats 快照 → 可读文本（key=value）→ publish_external 响应
- DataFactory::OnTick 每 10s 结构化指标日志（[data:stats] 单行 key=value）
- 配置：cpf/dpf/dts-test/tune 四组 dts 进程 + spa 对端加 oam 端点
- 测试：spa_test 增加 oam 拉取断言（发 req 收 resp），cross_process 覆盖

**功能验证（15:34 完整证据链）**：
```
dts: [data:oam] stats req received          ← req 到达 data 线程 oam 组
dts: published topic=DTS_oam_11 len=134     ← 指标响应发出（134B 文本）
spa: PASS (oam stats pull verified)         ← 对端收到响应
```

**沙箱跨进程环境限制定界（重要）**：
- 现象：多端点跨进程发现（cross_process 11 端点 / tune 11 端点）在沙箱当前状态
  不可靠（对端 reader 收 0）；**单端点**（plain_smoke / detmw_demo）稳定通过
- 定界：沙箱组播对大流量 SEDP 公告的投递劣化（与 32K UDP 分片不可达同源——
  沙箱网络栈限制；12:1x 前该环境可承载，之后劣化）。**非代码回归**（同二进制在
  手动逐进程 + 残留清理 + 发现窗口充足时全链路 PASS 过）
- 测试稳健性改进（保留，正常环境有益）：nfoam/spa 发送重试（发现前消息丢失自愈）、
  run_cross_test.sh sleep 3→5
- 排查过程中发现：dts_test 后台 job 下 kill -INT 不退出（bash 后台作业继承
  SIG_IGN），手动实验残留进程污染后续测试——已清理；测试脚本用 SIGTERM（正常）
