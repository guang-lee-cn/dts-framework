# 2026-08-20：WSL 断连根因（bucket_rtps OOM）+ 桶接收缓冲钳制修复 + P1-3 远程控制通道

## A. 断连事故根因（用户报障"两次 zcode 断连"，实为 4 次 OOM）

**现象**：08-17 16:23/16:32、08-20 17:21/17:23，ZCode 会话断连，08-20 一次伴随 WSL VM 整机重启。

**根因链（内核 journal 铁证，5 次 OOM 全同一凶手）**：

```
Out of memory: Killed process (bucket_rtps_tes) anon-rss ≈ 12.4~12.6GB ×2 进程
= 吃满 21.5GB WSL VM → OOM 连杀 → VM 崩溃重启 → 会话断连
```

**bug 本体（BucketTransport）**：
- FastDDS 非 secure 模式下参与者侧 `max_receiver_buffer_size = UINT32_MAX`，
  `NetworkFactory` 的 `min(transport->max_recv_buffer_size(), ...)` 两端都是上限值，**无封顶效果**；
- 内置 SHM 同样返回 UINT32_MAX 但不炸——它从段内**零拷贝读**，不按该值分配；
- 桶传输收线程 `std::vector<uint8_t> buf(max_msg_size_)` 预分配接收缓冲，拿到 UINT32_MAX
  → **每输入通道 vector(4GB) 且置零摸满**，每进程 3 通道（元组播/元单播/用户单播）= 12GB 常驻；
- 桶测试此前在无 /dev/shm 环境恒 Skipped，**08-17 16:23 首次真跑即 OOM**——worklog 2026-08-17
  "bucket_smoke/bucket_rtps → Skipped" 的记录只对沙箱成立，当日本机 16:23/16:32 实际真跑并崩了机。

**修复（一行钳制，OpenInputChannel）**：`effective = min(max_msg_size, 配置 maxMessageSize)`
（8MB）。受控复现（ulimit 3GB 护栏）：修复前 1s 内 bad_alloc；修复后 sub RSS **208MB/9 线程**，
`bucket_rtps 200×32K recv=200/200 gap=no PASS (lossless)`，pub 写入 19.7ms（~325MB/s，2 拷贝版）。

**教训**：
- 自定义 TransportInterface 的 `max_recv_buffer_size()` 语义 = "最大报文接收尺寸"，不是"能力上限"，
  消费方会拿它分配；抄内置 SHM 的返回值必须连它的"不分配"前提一起抄
- swap=0（.wslconfig 写了 swap=8GB 未生效，`free` 实测 0B）放大了事故：无缓冲直接 OOM+VM 崩

**环境噪声（与断连无关但同期存在）**：mirrored 网络 + dnsTunneling 全天 CheckConnection 失败
（本 boot 283 次/上 boot 782 次，开机 10s 即现），eth2 弹跳 + 时钟抖动；另 mw-bench 项目 zenoh
基准 16:07 同受累（64KB 吞吐 0 帧）。Windows 侧网络（VPN/WiFi/防火墙）待排查。

## B. P1-3 远程控制通道（D2/R5）：DDS 命令行 → control(CommandExecutor)

**实现**（D3"命令一处定义、传输两条"落地）：
- msgId：`MSG_ID_OAM_CMD_REQ=0x000C` / `MSG_ID_OAM_CMD_RESP=0x000D`（dts_def.h，协议注释在侧）
- gen_detmw.py：`INSTS + "control"` → 第四个恒定线程头 `control_routes.h`（空表允许，纯单线程进程可编）
- console.cpp：`control_submit_dds()`——detmw 接收回调直投 control 命令队列（Job 加 dds 标志），
  control 线程 `ctl::Execute` 后经 DDS 发布响应（载荷 `cmd=<命令行>\n<Execute输出>`，cmd 前缀供
  网管并发对答案）；空载荷/超长/control 停止时丢弃（Warn）；下电顺序保证发布时 DtsMw 存活
